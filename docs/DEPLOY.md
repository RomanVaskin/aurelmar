# Деплой AURELMAR на KZ

## Действующая площадка

По подтверждённой владельцем production-карте: `https://aurelmar.ru`,
KZ `213.155.29.140`, checkout `/opt/aurelmar`, только `aurelmar.service`,
Next.js `127.0.0.1:3280`, Node.js `22.23.2`, pnpm `12.3.4`.
Nginx, TLS, DNS и unit workflow не изменяет.

## Подтверждённая схема доступа

Изучен `.github/workflows/deploy.yml` в `RomanVaskin/olnoo-admin`:
SSH `root@213.155.29.140`, Secret **`KZ_SSH_KEY`**, обновление существующего
checkout через его `origin`. AURELMAR использует эту же схему SSH.
Ключи других приложений, Yandex и каталогов здесь не нужны.

SeaSmates не найден среди доступных через подключение GitHub репозиториев;
его workflow проверить не удалось. API списка Actions Secrets возвращает
`Forbidden`: наличие Secret именно в AURELMAR не подтверждено.
Значения секретов не запрашивались и не выводились.

## Настройка перед первым запуском (владельцем)

В `RomanVaskin/aurelmar` → Settings → Secrets and variables → Actions:

1. В **Secrets** добавить `KZ_SSH_KEY` либо предоставить этому репозиторию доступ
   к существующему organization Secret с тем же именем. Значение — существующий
   разрешённый deploy-ключ для `root@213.155.29.140`. GitHub не позволяет прочитать
   ключ из Secrets другого репозитория: использовать доверенное хранилище владельца.
   Не создавать новый ключ/доступ на сервере без отдельного согласования.
2. В **Variables** добавить новую переменную `KZ_SSH_KNOWN_HOSTS`:
   строку формата OpenSSH known_hosts для `213.155.29.140` (порт 22).
   Это публичный ключ хоста, не приватный ключ. Взять из уже доверенного
   known_hosts либо сверить с fingerprint через доверенную консоль сервера:
   `ssh-keygen -lf /etc/ssh/ssh_host_ed25519_key.pub`.
   `ssh-keyscan -t ed25519 213.155.29.140` может дать кандидата, но его fingerprint
   обязательно сверить отдельно, прежде чем сохранять переменную.
   В отличие от OLNOO Admin, workflow не доверяет результату нового keyscan
   во время каждого запуска. Отсутствующая переменная или несовпадение ключа
   останавливают деплой.
3. Подтвердить, что существующий `/opt/aurelmar` может выполнить
   `git fetch origin main` со своей серверной авторизацией. Workflow не передаёт
   GitHub-токен на сервер и не меняет `origin`.
4. Подтвердить доступность указанных версий `node` и `pnpm` в неинтерактивном
   SSH-сеансе root, а также место для временной сборки и её зависимостей в `/opt`.
   Workflow не устанавливает Node/pnpm, не меняет unit и не добавляет сервисы.

После отдельного разрешения владельца: настроить значения **до merge** PR.
Первый push в `main` после merge автоматически запускает Deploy AURELMAR.
Ручного `workflow_dispatch` нет. До разрешения владельца не выполнять merge.

## Порядок и границы

- Запуски сериализованы (`cancel-in-progress: false`), деплоится SHA события,
  проверенный как предок актуального `origin/main`.
- `git archive` создаёт временную сборку `/opt/aurelmar-build.*`. Существующие
  dotenv-файлы копируются без вывода содержимого; оригиналы не перезаписываются.
- `pnpm install --frozen-lockfile`, `pnpm exec tsc --noEmit`, `pnpm build` и
  наличие `.next/BUILD_ID` обязательны **до** изменения живого checkout.
  Отдельный tsc нужен: текущий Next config пропускает проверку типов при build.
  Сборке нужен доступ к npm registry и Google Fonts.
- Только после успеха обновляются checkout, `node_modules`, `.next`, затем
  перезапускается **только** `aurelmar.service`. Нет `git clean`, миграций,
  изменения конфигурации сервера или иных приложений.
- Проверяются `systemctl is-active --quiet aurelmar` и точный HTTP 200 от
  `http://127.0.0.1:3280/` с ограниченными попытками на время старта.
  Неуспех завершает job ошибкой, без бесконечных повторов.
- Временная сборка и SSH-файлы runner удаляются. При ошибке install/tsc/build
  живые код, зависимости и `.next` сохраняются, restart не выполняется.
  Это не система атомарных релизов/автоматического отката: ошибка уже на этапе
  продвижения или старта требует отдельной диагностики; автоматического rollback нет.

Живой SSH-доступ, unit и HTTP production в рамках подготовки PR не проверялись.
Merge, деплой и изменения production не выполнялись. После разрешённого запуска
проверить результат Actions и отдельно доступность `https://aurelmar.ru`.

## Проверки при подготовке

- `actionlint 1.7.7`, разбор YAML и `bash -n` всех встроенных скриптов — успешно.
- `tsc --noEmit`, `pnpm build`, `git diff --check` — успешно.
  Локальная среда: Node.js `24.19.0`, pnpm `11.19.0`; это не проверка
  production-версий. Workflow требует подтверждённые владельцем `22.23.2`/`12.3.4`.
- Локальное выполнение серверного скрипта с подменой команд (без SSH): ошибки
  install, tsc и build сохраняют живые файлы, не вызывают reset/restart;
  успешный путь перезапускает только AURELMAR; HTTP 503 заканчивается ошибкой
  после 15 попыток; dotenv сохраняется, временный каталог удаляется.
  Эти сценарии проверяют порядок операций, а не настоящий systemd или сеть.
